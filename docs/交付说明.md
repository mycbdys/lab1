## 二、8 个控制问题的答案

### Q1. 为什么密码哈希更推荐 bcrypt 而不是 SHA-256？

SHA-256 是为“快”设计的通用哈希，现代 GPU 每秒能算几十亿次；一旦数据库泄露，攻击者可以高速
暴力破解或查彩虹表。bcrypt 故意“慢”：基于 Blowfish key schedule，每个密码使用独立随机盐，
并且 cost 可调（本项目 cost=12），cost 每加 1，攻防双方的工作量都翻倍；盐让彩虹表失效，也让
相同密码得到不同哈希。bcrypt 内存开销小是它的局限，因此新系统更推荐内存硬的 Argon2id。SHA-256
适合做完整性校验和 HMAC，不适合存密码。本项目用 `bcrypt.checkpw` 校验，数据库中只存 `$2b$`
开头的哈希。

### Q2. SAST 与 DAST 的主要区别是什么？

SAST 是白盒静态测试：不运行程序，直接分析源码/字节码，能在 IDE 和 CI 中尽早发现危险写法
（字符串拼接 SQL、`eval`、弱加密等），并定位到文件和行号；缺点是误报较多，看不到运行时配置、
框架行为、认证状态和第三方服务。DAST 是黑盒动态测试：运行应用后通过 HTTP/UI 发请求，从攻击者
视角观察响应，能发现运行时才暴露的问题（某接口漏鉴权、配置错误、真实注入行为），误报相对少，
但介入晚、需要环境、代码覆盖率有限。两者互补：本作业 CI 里的 Bandit 是 SAST，Work 2 的
OWASP ZAP 是 DAST；成熟流程通常 SAST + DAST + SCA 一起用。

### Q3. JWT 的工作机制是什么？它包含哪些信息？服务器如何验证其真实性？

JWT 由三段 Base64URL 组成：`header.payload.signature`。header 声明算法和类型（如
`{"alg":"HS256","typ":"JWT"}`）；payload 是 claims，包括 `sub`（用户 id）、`iat`、`nbf`、
`exp`、`iss`、`aud`、`jti` 以及业务字段（如 username）；signature 是对
`base64url(header)+"."+base64url(payload)` 用服务器密钥做 HMAC-SHA256（或私钥做 RS256/ES256）
得到的签名。

服务器不会“解出 payload 就相信”。它用密钥重算签名并做常量时间比较，确认 `alg` 是预期算法
（绝不能接受 `none` 或攻击者指定的算法），检查 `exp`/`nbf`，校验 `iss` 和 `aud`，然后才用 `sub`
查用户。payload 只是签名、不是加密，所以不能放密码、密钥或隐私数据。JWT 无状态、易扩展，但
难以立即撤销，因此要用短 TTL、`jti` 黑名单或 refresh token 轮换。本项目 HS256、15 分钟过期，
`jwt.decode` 固定 `algorithms=["HS256"]` 并校验 audience/issuer，篡改、过期和 `alg=none`
都会被拒绝。

### Q4. 不审计第三方依赖会带来哪些风险？

现代应用大部分代码来自第三方：这个小 Flask API 有几十个传递依赖，两个直接依赖的 Node demo
实际装了 77 个包。不审计就等于继承整棵依赖树里的所有已知漏洞——一个过时的模板引擎就可能变成
RCE，本作业的 CVE-2022-29078（EJS 3.1.6）就是实例。其他风险包括：供应链攻击（typosquatting、
维护者账号被劫持、恶意 install 脚本）、无人维护的包、传递依赖被意外升级、许可证不合规，以及
带漏洞的构建/测试工具进入 CI。依赖还会随时间“变坏”：发布时干净的版本，后来可能被披露漏洞。
没有持续 SCA 和 SBOM，就不知道自己到底发布了什么。缓解办法是锁定版本、每次构建跑 SCA
（pip-audit、OWASP Dependency-Check、`npm audit`）、跟踪公告、删除不用的包，并保留 SBOM，
以便下一次 Log4Shell 式事件时快速定位受影响系统。

### Q5. 用 Docker 和 Vulhub 学习网络安全，比直接在机器上安装漏洞软件有什么优势？

Docker 把漏洞服务隔离在容器里：独立文件系统、网络命名空间和固定依赖。宿主机保持干净，打错
或执行恶意 payload 的影响被限制在可丢弃的容器内，`docker compose down -v` 就能清空。环境可
复现：同一镜像和 compose 文件在每台电脑、CI 上都得到相同版本，这对“只影响某个版本”的 CVE
尤其重要；依赖冲突也消失，因为旧版漏洞库装在镜像里而不是系统 Python/Node 中。多服务靶场
（数据库、Web 服务器、应用）一条命令启动，快照可回到干净状态，端口可以只映射到
`127.0.0.1`。

Vulhub 进一步提供现成的 compose 文件和 README，写清楚漏洞版本、启动命令和利用步骤，学习者
可以把精力放在漏洞本身而不是重建旧环境。直接安装漏洞软件则可能感染宿主机、破坏系统包、留下
后门且难以卸载。Docker 不是完美隔离（共享内核、特权 daemon、镜像供应链），容器仍应视为不可信，
更不能暴露到公网。

### Q6. 漏洞（vulnerability）和利用（exploit）有什么区别？本次复现的是什么？

漏洞是代码、配置或设计中的弱点，可能导致安全影响——例如 EJS 3.1.6 把 `outputFunctionName`
直接拼进生成的 JavaScript，而应用又把 `req.query` 整体传给 `res.render`。漏洞无论有没有人攻击
都存在。利用是具体的技术、输入或工具，用来触发漏洞并造成效果：本作业的利用是一个特制的 HTTP
查询参数，它闭合生成的 `var` 语句，调用
`process.mainModule.require("child_process").execSync(...)`，并用末尾的 `s` 让生成代码保持
语法合法。

本次复现的是 **CVE-2022-29078 的利用过程**：在受控的 EJS 3.1.6 环境中，请求让服务器执行
`whoami` 并把结果写入 `pwned.txt`，而 HTTP 响应仍然是 200 和正常页面。漏洞是不安全的选项注入，
利用是那个具体请求和 payload；复现证明漏洞可达、影响真实，根因分析解释为什么 payload 有效，
修复则消除使利用成立的条件。

### Q7. 打完补丁后，为什么必须做回归测试，确认主功能没有被破坏？

补丁会改代码、配置或依赖版本，任何改动都可能破坏用户依赖的行为：升级可能改变 API、错误处理、
性能或模板语义；代码修复可能误拒合法输入、改变响应格式或破坏登录流程。没有回归测试，可能上线
一个“安全但不可用”的系统——用户登不上、数据丢失、正常请求 500，比漏洞本身更糟。回归测试还能
发现修复不完整：如果原攻击仍能从另一条路径成功，说明漏洞没有真正消除。它同时把预期行为固化
下来，防止未来改动悄悄重新引入问题，也让团队在压力下能快速、有信心地发布。

本项目从三个层面验证：同样的利用请求不再生成 `pwned.txt`；正常页面仍显示 `Hello, guest!`；
库层直接拒绝恶意选项并报 `outputFunctionName is not a valid JS identifier.`。同时 API 的
21 个自动化测试（登录、token 校验、数据访问、转义、限流）在安全改动后全部通过，这正是手册
要求的回归检查。

### Q8. 了解和复现已知 CVE，对安全从业者（如渗透测试员或 SOC 分析师）有什么帮助？

对渗透测试员，复现 CVE 能积累真实的攻击原语：payload 长什么样、需要什么前置条件、应用如何
响应、如何在不破坏目标的前提下验证影响。这能让测试更快、更贴近真实攻击，按“可利用性”而不是
扫描器分数排优先级，并用安全的 PoC 证明漏洞、再验证修复是否真的阻断了攻击。

对 SOC 分析师，同样的知识能提升检测与响应：复现会暴露利用产生的日志、HTTP 参数、进程创建和
文件写入，检测工程师据此编写 SIEM 规则、WAF 签名和 IDS 特征，抓住行为而不是单个 IP；还能用于
告警研判（这是不是已知的 EJS payload？）、威胁狩猎、事件响应，以及漏洞管理——优先处理暴露在
公网、运行受影响版本的系统，尤其是进入 CISA KEV 或有公开利用的 CVE。

复现还培养安全习惯：在隔离环境操作、记录精确版本、使用最小 payload、事后清理。这种“攻击理解
+ 防御映射”的结合，才能把一串 CVE 编号变成可执行的安全工作。

## 四、如何运行

```powershell
# 1. 安装依赖（建议虚拟环境）
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements-dev.txt

# 2. 初始化演示数据库（alice / Alice#2026，bob / Bob#2026）
python scripts\seed.py

# 3. 启动 API（默认 http://127.0.0.1:5000；如端口被占用可设 $env:PORT）
python run.py

# 4. 运行测试
pytest -q

# 5. 运行扫描
bandit -r app -f json -o security/bandit-report.json
pip-audit -r requirements.txt --format json -o security/pip-audit-report.json

# 6. 一键 API 演示（写入 evidence/api-demo.txt）
powershell -ExecutionPolicy Bypass -File scripts\api_demo.ps1
```

CVE 复现：

```powershell
cd cve\CVE-2022-29078\vulnerable
npm install
node app.js                       # http://127.0.0.1:3000

cd ..
powershell -ExecutionPolicy Bypass -File run_demo.ps1 -Mode vulnerable
powershell -ExecutionPolicy Bypass -File run_demo.ps1 -Mode fixed
```

有 Docker 的机器上：

```bash
cd cve/CVE-2022-29078
docker compose up --build
docker compose -f docker-compose.fixed.yml up --build
```
